# ADR-001: отдельный Identity Service

Статус: принято.

Дата: 2026-08-17.

## Контекст

Семейное дерево развивается как модульный монолит на Go. При этом аутентификация пользователей должна быть вынесена в отдельный сервис и вызываться основным HTTP API по gRPC.

Разделение вводится как осознанное учебное и архитектурное исключение. Остальные предметные модули не следует выделять в микросервисы без измеренной причины.

## Решение

Система состоит из двух backend-приложений:

1. `family_tree_app` — публичный HTTP API и модульный монолит семейного домена.
2. `family-tree-identity-service` — внутренний gRPC-сервис учётных записей и сессий.

Браузер не обращается к gRPC напрямую. Публичные HTTP endpoints `/api/v1/auth/*` принадлежат Family API и преобразуют запросы в вызовы `identity.v1.IdentityService`.

### Identity Service владеет

- аккаунтами и статусами аккаунтов;
- email и его подтверждением;
- password hash;
- одноразовыми токенами подтверждения и восстановления;
- пользовательскими сессиями и hash refresh token;
- ротацией и отзывом refresh token;
- выпуском и проверяемыми ключами подписи access token.

### Family API владеет

- деревьями и участниками деревьев;
- персонами, именами, событиями и местами;
- родственными связями и семейными союзами;
- метаданными медиа;
- экспортами и аудитом семейных данных.

`User` учётной записи и `Person` в дереве остаются разными сущностями. Family API использует UUID пользователя как внешний идентификатор субъекта доступа, но не хранит его пароль, refresh token или одноразовые auth-токены.

## Данные и согласованность

- Сервисы владеют разными базами PostgreSQL либо изолированными схемами с разными пользователями БД.
- Между хранилищами сервисов нет SQL join и внешних ключей.
- `tree_members.user_id` содержит UUID, выпущенный Identity Service, и проверяется на уровне сценариев приложения.
- Распределённая транзакция между сервисами не используется.
- Локальная проекция профиля пользователя, если понадобится, создаётся идемпотентно и не становится источником истины для credentials или sessions.

## Токены и транспорт

- Access token короткоживущий и подписывается асимметричным ключом.
- Family API проверяет access token локально по публичному ключу, не вызывая gRPC на каждом запросе.
- Refresh token является непрозрачным секретом, хранится у клиента только в `HttpOnly + Secure + SameSite` cookie, а в Identity Service — только в виде hash.
- Обновление токена выполняет ротацию; повторное использование старого refresh token отзывает затронутую сессию.
- Внутренние gRPC-вызовы используют deadlines, request ID и защищённый транспорт в production.
- Повторять автоматически можно только идемпотентные gRPC-операции.

## Последствия

Плюсы:

- credentials и сессии изолированы от семейного домена;
- граница auth явно выражена контрактом `identity.v1`;
- основной backend сохраняет модульную структуру;
- Identity Service можно развивать и тестировать отдельно.

Цена решения:

- два приложения, две схемы миграций и два контура наблюдаемости;
- необходимо отображать gRPC-ошибки в единый HTTP error contract;
- нужно определить поведение Family API при недоступности Identity Service;
- локальная разработка и end-to-end тесты требуют запуска двух сервисов.

## Не входит в решение

- выделение остальных feature-модулей в микросервисы;
- общая база данных как публичный контракт между сервисами;
- синхронная introspection access token на каждом запросе;
- Redis, брокер сообщений или event sourcing до появления измеренной необходимости.
